# Dataset interfaces

## Fine-Tennis10

Fine-Tennis10 will be made publicly available upon acceptance of the paper.

```text
data/Fine-Tennis10/dataset/
├── labels.txt
├── train/
│   ├── annotation.txt
│   └── <sample>.json
├── test/
│   ├── annotation.txt
│   └── <sample>.json
└── ball/
    └── <sample>_ball.csv
```

The JSON object contains `file_name` (the filename stem) and `skeletons`, a list of frames with 17 H36M joints and three coordinates per joint. Each annotation line is `<sample>.json <integer-class-id>`. Class IDs range from 0 to 9. `labels.txt` contains class names followed by their integer IDs. These files are supplied with the dataset; no real annotations or labels are bundled here.

Ball CSV columns are `Frame,Visibility,X,Y`. Frame indices are zero-based within the clip. Visible coordinates are in image pixels; the public configs specify `image_wh: [1920,1080]`. Missing observations retain a separate visibility mask through interpolation and descriptor construction. The loader returns skeletons `(3,64,17,1)`, ball features `(7,64)`, visibility `(64,)`, a label, a sample name and target frame positions. Ball features contain six motion descriptors plus visibility. Bone streams use the explicit H36M parent map in the feeder.

The primary split is class-stratified at clip level. The released train/test folders correspond to this protocol. They are not a player-disjoint partition.

## BadmintonDB

Use the uncollated BadmintonDB arrays from the [official BST resource](https://github.com/Va6lue/BST-Badminton-Stroke-type-Transformer#reproducing-the-results). Obtain the underlying dataset through [BadmintonDB](https://github.com/kwban/badminton-db).

```text
data/BadmintonDB/dataset_npy/
├── train/<class>/<sample>_joints.npy
├── train/<class>/<sample>_shuttle.npy
├── val/<class>/<sample>_joints.npy
├── val/<class>/<sample>_shuttle.npy
├── test/<class>/<sample>_joints.npy
└── test/<class>/<sample>_shuttle.npy
```

Use the upstream prepared coordinate representation without applying an additional normalization. Joint arrays have shape `(T,2,17,2)` and shuttle arrays `(T,2)`. The two player axes must retain the upstream order. Zero shuttle coordinates denote missing observations. Upstream preparation expresses joints relative to player bounding boxes and shuttle coordinates relative to video resolution.

Class directories use `Top-` or `Bottom-` followed by `Block`, `Clear`, `Drive`, `Dropshot`, `Net-Kill`, `Net-Lift`, `Net-Shot`, `Serve` or `Smash`. The loader also accepts `Top-Flick-Serve` and `Bottom-Flick-Serve`, mapping each to the corresponding serve class. Class IDs follow the explicit `CLASS_LIST_18` in `feeders/badmintondb.py`.

The fixed split contains 6,120 / 757 / 781 clips. The validation command checks counts before training-time balancing. Training replicates each class to the largest class count. No split is generated by this repository.

The feeder retains the source temporal routine: integer-stride sampling for long clips and end padding for short clips, targeting 72 frames. Joint and bone channels are concatenated to `(4,72,17,2)`; the shared shuttle descriptors are `(7,72)`. The feeder returns target frame positions to the trainer. Its internally calculated valid length is not returned as a separate model input.

The interaction model applies one shared encoder to both players, adds learned player identity embeddings, and fuses role-embedded player and shuttle tokens. It classifies the ordered concatenation of player tokens. Training selects checkpoints by validation Macro-F1; `scripts/evaluate.py` uses the test split.
